Running it

Everything is in two repositories and reproducible from them. kobo-espo has this instance's setup, forms, templates, tests and this manual. kobo-espo-bridge has the bridge. A few things are done by hand, and they're listed.

From nothing

# .env: ESPO_HOST, ESPO_SSH, KOBO_URL, KOBO_TOKEN (a test or bridge account's)
deploy/up.sh                       # EspoCRM 10.0.11, MariaDB, its scheduler, Caddy (TLS)
tests/fetch-secrets.sh             # the admin password, to secrets/ (not in git)
python3 -I espo/seed/seed.py --users   # entities, fields, board, roles, teams, formulas, test users
deploy/bridges.sh                  # kobo-espo-bridge's setup for each template, then the bridges

Each step can be run again: they all keep what's there and put back what they define.

  • deploy/up.sh generates the passwords on the server, the first time.
  • The seed makes the Response, Site and Standard entities, the task board's columns, the five roles, the teams, and the formula scripts (espo/formula/).
  • Setup makes each form's fields, and an API user that can do only what that form needs.

EspoCRM 10 doesn't install with all of /var/www/html on one volume (the "legacy" layout): mount data, custom and client/custom separately, as docker-compose.yml does. And publish it only once it has installed itself: its installer is open until then, and scanners found it within seconds.

A new consortium or response

A consortium (Workflow A):

  1. Add its choice to the support form's project question, and redeploy it.
  2. Add a [[route]] to support-request.toml: the choice, its team ("Project: …"), who to notify and who to escalate to.
  3. Run deploy/bridges.sh. It makes the team, and the case field gets the new choice from the form.
  4. Give the consortium's people their role and that team (below).

A response (Workflow B):

  1. Create its team ("Response: …") in Administration → Teams.
  2. Create the response, with that team and its lead. It starts with its four tasks.
  3. Give its people the team.
  4. For its sites, copy site-visit.toml with the new team and its visit form's name, and run deploy/bridges.sh.

People and roles

Administration → Users → Create. Give each person a role:

  • Internal Staff, Support Triager, Partner Staff;
  • Roster Expert, Volunteer.

Then give them the teams of the projects and responses they work on, and nothing more. What each role may do is on the overview, and in espo/seed/seed.py.

  • A volunteer who's deployed (from the roster, a contact with profile Volunteer) becomes a user by hand: role Volunteer, the response's team. It's deliberately not automatic.
  • Someone who leaves: take them out of the team, and reassign their open tasks.

The rest of the manual steps (saved board filters, SMTP, sharing forms with a bridge account) are in docs/manual-steps.md.

Checking on the bridge

deploy/bridges.sh logs             # what each bridge did: ids and counts, never answers
ssh root@<droplet> docker exec kobo-espo-bridge-intake-1 \
    python3 -I /bridge/bridge.py failed /state/intake    # submissions waiting, and why

Each bridge writes status.json in its state directory: its last good pass, its counts, how many submissions are waiting and the oldest one's reason. A submission waiting for a fix (a choice missing in EspoCRM, a required answer missing) is retried by itself. It's retried at once when the template or the form changes.

Run one bridge per template. Two at once could both make a record for the same new submission: each looks for it first, but neither can see the other's in flight.

Agents

Agents are set up in EspoCRM (Administration → Agents): what a record must look like for one to start, its instructions, its routes and which model it uses. One runner, agents/runner.py, does the work for all of them. On the droplet it's the agent-runner container:

deploy/agents.sh                   # an API user and role per Agent (agents/sync.py), then the runner
deploy/agents.sh sync              # only that, after adding an Agent
deploy/agents.sh down | logs

Agents that use rules only need nothing else. Agents with a model call Claude, and there are two ways to reach it:

  • The Claude API (AGENTS_LLM=real, the default): ANTHROPIC_API_KEY in .env, which deploy/agents.sh copies to the droplet. This is the only way with web search and fetch, and with the fallback to another model when one declines.
  • Amazon Bedrock (AGENTS_LLM=bedrock): your AWS login (for example an SSO profile, with AWS_PROFILE and AWS_REGION set), no Anthropic key. Bedrock has no web tools: an agent that lists them runs without them, and its note says so. A model that declines fails the attempt.

Without either, an agent with a model fails its runs and takes its failure route.

Running the agents on your own machine

For trying agents with a real model before the droplet has a key. Your runner works on the droplet's EspoCRM, so stop the droplet's runner first. Otherwise both runners pick up the same records.

python3 -m venv .venv && .venv/bin/pip install "anthropic[bedrock]"
deploy/agents.sh down
python3 -I tests/agent-examples.py         # records for the example agents ("BDR …")
AGENTS_LLM=bedrock AGENTS_MODEL=claude-sonnet-5-5 \
  ESPO_URL=https://espo-test.kobolabs.dev ESPO_SITE_URL=https://espo-test.kobolabs.dev \
  .venv/bin/python -I -u agents/runner.py once
deploy/agents.sh up

AGENTS_MODEL overrides the model set on each Agent. Use Claude Sonnet 5.5 for test runs to keep the cost down. A pass over the three examples costs about one US cent on Sonnet 5.5, and about three on Opus 5.5. Each run (Administration → Agent runs) records the model, the tokens and the cost. The examples are in dry run: they post a note saying what they would do and change nothing else.

A record is worked on once per trigger (per stage reached, or per new visit note). To run an agent again, give it a new record or a new note; changing the agent doesn't redo old records.

The tests

tests/run_all.sh                   # unit tests, seed, isolation, board, connection (fake Kobo)
tests/run_all.sh --kobo real       # the connection tests on the Kobo account in .env
python3 -I tests/cases/latency.py  # submission to record, through the running bridges

The tests make their own records (named "ISO …" and "WFB …", and cases with a run number). site/demo-data.py clears the instance and fills it with the made-up demo data again. site/shots.py takes this manual's screenshots, and site/build.py builds its pages.

Rules worth keeping

  • Teams are the boundary. Non-staff roles read "team" or "own", never "all", except the shared standards.
  • Keep the formula scripts. They refuse an assignee or collaborator outside the record's team, keep a case in one team, give tasks and sites their response's team, drop old assignees from collaborators, and hand tasks back when a response closes. Several close gaps EspoCRM's own permissions leave.
  • Administrators see everything, and fields, layouts and automations are instance-wide. Keep administrators few.
  • The bridge's users can't read users or delete anything. The intake user reads all cases, contacts and accounts, which it needs to find requesters and avoid duplicates. Keep its key on the server only.
