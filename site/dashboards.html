Dashboards of EspoCRM's records

EspoCRM is for following up; charts and maps are kobo-dash's. A dashboard reads a project's sites, or a response's 5W, through a feed: EspoCRM's records kept as a table that follows EspoCRM, read by an API user that can see only what the dashboard needs.

  1. A feed user

    In EspoCRM: one team's records of one kind, only the fields needed, read only.

  2. Its key

    Copied from EspoCRM into kobo-dash's admin page, never into a chat.

  3. Feeds and a dashboard

    Made with kobo-mcp; the dashboard updates as EspoCRM changes.

The feed user

The EspoCRM MCP's create_dashboard_feed makes an API user for one dashboard feed:

  • it reads one kind of record (sites, activities, activity locations, organisations);
  • of one team: a cluster project's own (that project only), a response's (all its projects), or a team named directly (a country's CSOs, CSO: Kenya: see CSO mapping);
  • only the fields chosen: EspoCRM's field-level access hides the rest;
  • and it writes nothing.

Records about people (contacts, users, focal points) and files are refused. list_dashboard_feeds lists these users; remove_dashboard_feed removes one, and its key stops working at once. In testing, each user's own key read only its team's records and fields, and was refused everything else.

Its key, in kobo-dash

An admin opens the user's page in EspoCRM (the MCP gives the link), copies its API key, and pastes it into kobo-dash's admin page, in the EspoCRM card, with EspoCRM's address and a name. kobo-dash checks it, refuses an administrator's or a person's key, and stores it encrypted. The key is never in a chat: neither MCP asks for it or shows it.

Feeds

A feed keeps one kind of record, some of its fields and a filter, as a table in the dashboard owner's kobo-dash library. Its columns come from EspoCRM, with EspoCRM's labels (an owner's own labels are kept when the feed reads again): choices with EspoCRM's labels (the 5W's sectors, statuses, location types), several choices, numbers, dates, a linked record by its name, and latitude and longitude as a map point.

Every five minutes kobo-dash asks EspoCRM whether anything changed; when it did, the feed reads the records again and open dashboards update by themselves. Edits, new records and deletions all show. A feed's table is the feed's only: an upload can't replace it.

From a conversation

With both servers connected (kobo-mcp, and the EspoCRM MCP: see Connecting a form), ask for what the dashboard should show, e.g. “A dashboard of the ETC project's activity locations on a map, people reached by parish”. kobo-mcp's prompt A dashboard of EspoCRM records has the steps:

  1. create_dashboard_feed (EspoCRM MCP): shows what the user would read, then makes it;
  2. you paste its key into kobo-dash's admin page;
  3. create_espo_feed (kobo-mcp) for each kind of record, then create_dashboard, add_dashboard_table and the layout.

What viewers see

A dashboard's viewers are whoever its link or password reaches: EspoCRM's teams don't apply there. What it can show is decided in EspoCRM, by the feed user's team and fields. Keep personal data out of feeds; counts, statuses and places are what dashboards are for.

Limits

  • A dashboard starts from a Kobo project its owner owns or manages, then adds feeds: a dashboard of EspoCRM records alone isn't possible yet.
  • The owner needs a Kobo account.
  • kobo-dash runs on staging (staging.dash.kobolabs.dev) for now.
  • A feed holds at most 50,000 records: filter a bigger one.
